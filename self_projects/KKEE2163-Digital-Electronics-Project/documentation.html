A. SPI Master — Module Overview & Ports

What is spi_master?

spi_master.v is a bit-banging SPI controller that communicates with the ADXL362 3-axis accelerometer on the Nexys A7 board. It implements SPI Mode 0 (CPOL=0, CPHA=0) — meaning the clock idles LOW, and data is sampled on the rising edge of SCLK. The module uses a 93-state FSM driven by a global tick counter to manage every single SPI bit transition manually. There is no shift register or generic SPI engine — each bit sent/received gets its own dedicated FSM state.

B. SPI Clock Derivation — 4 MHz → 1 MHz SCLK

Step 1: 100 MHz → 4 MHz (iclk_gen.v)

The board provides 100 MHz. iclk_gen divides by 25 to get 4 MHz.

Math: 100 MHz / 4 MHz = 25 ticks per period.
Since 25 is odd, a 50/50 duty cycle is impossible. Solution: toggle at tick 13 and 25, giving 13 HIGH + 12 LOW = 52% duty cycle (close enough for SPI).

counter: 0─1─2─...─12─13─14─...─24─0─1
clk_reg: ▓▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░░░▓▓
         │←── 13 HIGH ──►│◄─ 12 LOW ─►│

Step 2: 4 MHz → 1 MHz (Inside spi_master.v)

Inside spi_master, a 1-bit counter (clk_counter) divides by 4:

Math: 4 MHz / (2 × 2) = 1 MHz. The counter flips every 2 iclk ticks.
This 1 MHz signal (clk_reg) is gated by sclk_control:

assign sclk = sclk_control ? clk_reg : 0;

When sclk_control = 0: SCLK stuck LOW (idle)
When sclk_control = 1: SCLK = 1 MHz toggle

Why 4 Ticks Per SPI Bit?

Each SPI bit takes 4 iclk ticks (= 1 µs at 4 MHz = one period of the 1 MHz SCLK).
The FSM advances states every 4 counter ticks. For example, SEND_WCMD7 starts at counter=24002 and transitions to SEND_WCMD6 at counter=24005 → that's a 4-tick span = 1 SCLK cycle. This is why you see every state spanning exactly 4 counter values in the Verilog code.

The entire FSM runs on a single always @(posedge iclk) block with a global counter register. State transitions happen at specific counter values — no separate clock; just a big case statement.

📖 Code Walkthrough — Write States (Lines 177–338)

The write sequence follows this exact pattern:

  1. POWER_UP (L177-180): Waits until counter == 23999 (= 24,000 ticks × 250 ns = 6 ms). This gives the ADXL362 time to finish its internal power-on reset.
  2. BEGIN_SPIW (L184-189): At counter == 24001, pulls cs <= 0 to select the slave and transitions to SEND_WCMD7.
  3. SEND_WCMD[7:0] (L193-233): Each state drives mosi <= write_instr[N] where N goes from 7 down to 0. States transition every 4 ticks. sclk_control is set to 1 at the first bit state, enabling the 1 MHz clock.
  4. SEND_WADDR[7:0] (L237-276): Same pattern, shifts out mode_reg_addr = 0x2D bit by bit.
  5. SEND_BYTE[7:0] (L280-330): Shifts out mode_wr_data = 0x02. On the LAST bit (SEND_BYTE0), at counter == 24097: resets counter to 0, pulls CS high, disables SCLK, and transitions to WAIT.
  6. WAIT (L334-339): Waits counter == 160002 (= 40 ms). The ADXL362 datasheet requires waiting for the first valid measurement to be ready. Then transitions to BEGIN_SPIR for the read loop.

E. SPI Read Transaction — 6-Byte Burst Read

After initialization, the SPI master enters an infinite read loop. Each iteration reads 6 consecutive bytes from the ADXL362 starting at address 0x0E (X_DATA_L). The ADXL362 auto-increments the address after each byte, so we get X_L, X_H, Y_L, Y_H, Z_L, Z_H in one continuous transaction.

📖 Code Walkthrough — Read & Receive States (Lines 341–706)

The read loop follows this pattern (repeats forever at ~100 Hz):

  1. BEGIN_SPIR (L343-350): Resets counter, at counter == 1 pulls CS low and enables SCLK simultaneously.
  2. SEND_RCMD[7:0] (L354-393): Shifts out read_instr = 0x0B on MOSI. Each state spans 4 counter ticks. Counter starts at 2 here (not 0) because BEGIN_SPIR consumed tick 0-1.
  3. SEND_RADDR[7:0] (L397-436): Shifts out x_LSB_addr = 0x0E on MOSI. After this, the ADXL362 knows we want to read starting from register 0x0E.
  4. REC_XLSB[7:0] through REC_ZMSB[7:0] (L440-697): 48 receive states. Each state samples MISO directly into the appropriate bit position: e.g., X[7] <= miso in REC_XLSB7. The ADXL362 auto-increments the register pointer, so bytes come in order: X_L, X_H, Y_L, Y_H, Z_L, Z_H.
  5. REC_ZMSB0 (L690-697): After the last received bit, at counter == 256: CS goes high, SCLK disabled, transitions to END_SPI.
  6. END_SPI (L701-706): At counter == 258, the latch_data signal fires, capturing packed data into temp_DATA. Then waits until counter == 40259 (= 10 ms inter-read gap) before looping back to BEGIN_SPIR.

Key detail: The MISO data is sampled at the beginning of each state (on the posedge of iclk), which aligns with the rising edge of SCLK (SPI Mode 0 compliance). The 4-tick-per-state design ensures the slave has time to set up its MISO before the next rising edge.

F. Data Packing — 16-bit Raw → 5-bit Per Axis → 15-bit Bus

Each axis of the ADXL362 outputs a 12-bit signed value in a 16-bit register. The SPI master keeps only the top 5 bits [11:7] of each axis, giving sign + 4-bit magnitude. The 3 axes pack into a single 15-bit bus.

G. Action FSM — Module Overview & Ports

What is action_fsm?

action_fsm.v is the game brain — it receives the 15-bit accelerometer data from spi_master, runs a 6-state FSM (IDLE → INIT → THROW → PULL → TURN → DONE), and detects gestures to score points. It uses a self-calibrating baseline to distinguish real motion from static tilt, and applies edge detection + cooldown debounce to prevent multiple triggers from a single gesture. The game runs for exactly 28 seconds (4s INIT + 8s × 3 phases).

Parameter: CYCLES_PER_SEC

The module has one parameter: CYCLES_PER_SEC (default = 100,000,000 for 100 MHz). This defines how many clock cycles equal 1 second. In the testbench, this is overridden to 1,000 to make the simulation run 100,000× faster (28 seconds of game time = 280 µs of simulation time). All timing — phase durations, cooldowns, baseline update rate — scales proportionally with this parameter.

H. Action FSM — 6-State Machine (Complete)

S_IDLE (state=0) — Lines 133–143

Clears ALL registers (score, timer, cooldown, throw_armed, turn_flips). Baselines snap to live accelerometer reading. Immediately transitions to S_INIT (start is guaranteed HIGH here because !start holds the FSM in the reset block above).

S_INIT (state=1) — Lines 145–154

4-second calibration period. No scoring happens. The self-calibrating baseline slowly tracks the resting accelerometer level. After 4 second-ticks, transitions to S_THROW with cooldown and throw_armed reset to 0.

S_THROW (state=2) — Lines 157–175

8 seconds. Two-step scoring: first a Z-axis spike rising edge sets throw_armed=1, then an X-axis spike rising edge scores +1 and resets armed. Cooldown 0.25s prevents rapid-fire. After 8s → S_PULL.

S_PULL (state=3) — Lines 178–192

8 seconds. Single-step scoring: any X-axis deviation rising edge (threshold ≥ 2 from baseline) scores +1. Lowest threshold = easiest phase. Cooldown 0.25s. After 8s → S_TURN.

S_TURN (state=4) — Lines 195–225

8 seconds. Counts sign flips on Y and Z axes (pooled counter). Every 2 flips = 1 point. Magnitude must be ≥ 4 (noise gate). Counter resets after scoring + 0.25s cooldown. After 8s → S_DONE.

S_DONE (state=5) — Line 227

Terminal state. Score is frozen. Self-loops forever. Only way out: SW0 → LOW triggers the !start reset block, which jumps back to S_IDLE and clears everything.

I. Self-Calibrating Baseline System

Why Baselines?

Without baselines, a tilted board would constantly report high X or Z values, triggering false scores. The baseline system measures the "resting" level of each axis and only counts deviation from baseline as motion. This means you can hold the board at any angle and it won't score — only actual movement (jerks, twists) will.

During IDLE: Instant Snap

if (state == S_IDLE) begin
  base_x <= x_w; // snap to live reading
  base_z <= z_w; // instantly
  base_div <= 0;
end

In IDLE, baselines copy the current reading every clock cycle. No delay.

During Gameplay: Slow Drift

// Every BASE_PERIOD cycles (= 1/16 sec):
if (x_w > base_x) base_x <= base_x + 1;
if (x_w < base_x) base_x <= base_x - 1;
// Same for Z axis

During gameplay, baseline moves ±1 step every CYCLES_PER_SEC/16 cycles = 16 Hz. This is slow enough that fast gestures create spikes above the baseline, but slow enough that gravity drift is absorbed.

Deviation Calculation (Lines 80-81)

wire [5:0] x_dev = (x_w > base_x) ? (x_w - base_x) : (base_x - x_w); // |x - baseline|
wire [5:0] z_dev = (z_w > base_z) ? (z_w - base_z) : (base_z - z_w); // |z - baseline|

Absolute difference — works regardless of direction. 6-bit width (range 0–63) is more than enough since magnitude is only 4 bits (0–15 max).

J. Scoring Algorithms — All 3 Phases (Complete)

🤾 THROW Scoring (Lines 157–175) — Two-Step, Threshold ≥ 5

Step 1 (ARM): A rising edge on z_dev ≥ 5 sets throw_armed = 1. This detects the upward jerk of a throwing motion.
Step 2 (SCORE): While armed, a rising edge on x_dev ≥ 5 scores +1, clears armed, and starts 0.25s cooldown.
Why two-step? Single-axis bumps (putting the board down, accidental tilts) only trigger one axis. A real throw involves Z-lift then X-thrust.

💪 PULL Scoring (Lines 178–192) — Single Spike, Threshold ≥ 2 (EASIEST)

Any X-axis deviation rising edge ≥ 2 from baseline scores immediately. No arming needed. The low threshold (DTH_PULL = 2, vs DTH_THROW = 5) makes this the most sensitive and easiest phase. A gentle tug in any direction is enough.

🔄 TURN Scoring (Lines 195–225) — Sign-Flip Counter (2 flips = 1 point)

Counts direction reversals on Y and Z axes. Both axes feed into a single turn_flips counter. When turn_flips ≥ 2, score +1 and reset the counter. Magnitude ≥ 4 acts as a noise gate (ignoring small tremors).

If y_mag ≥ 4 AND y_seen=0 → record first sign, set y_seen=1 2. If y_mag ≥ 4 AND y_sign ≠ y_last_sign → flip! turn_flips++ 3. Same for Z axis (pooled into same counter) 4. If turn_flips ≥ 2 → final_marks++, turn_flips=0, cooldown=0.25s

⏸️ Cooldown Debounce (All Phases)

After every point scored, a cooldown counter is loaded with CYCLES_PER_SEC/4 - 1 (= 0.25 seconds). While cooldown ≠ 0, no new scoring is possible — the counter decrements by 1 each clock cycle. This prevents a single sustained gesture from scoring multiple points and gives the player clear feedback that each gesture is a discrete action.

COOLDOWN_CYCLES = CYCLES_PER_SEC / 4 = 100_000_000 / 4 = 25,000,000 cycles = 0.25 sec
In testbench (CYCLES_PER_SEC=1000): COOLDOWN_CYCLES = 250 cycles = 2.5 µs

sec_count increments 0→1→2→3→... on each sec_tick. Subtracting from the phase length gives a countdown. This is a combinational output (always @*), so it updates instantly when sec_count changes.

How the Testbench Slave Works

The testbench contains a behavioral ADXL362 model (lines 56–152). Instead of counting SCLK edges like a real SPI slave, it peeks at the DUT's internal state_reg via hierarchical reference (dut.state_reg). When the master is in a REC_* state (about to sample MISO), the model combinationally drives the correct bit of the corresponding data byte. This guarantees perfect bit alignment without fragile edge counting.

How the Testbench Creates Gestures

The testbench directly drives the acl_data input bus using predefined constants:
REST = {0,0000,0,0000,0,1000} (Z mag=8, simulating 1g gravity at rest)
Z_SPIKE = {0,0000,0,0000,0,1111} (Z mag=15, big Z jerk)
X_SPIKE = {0,1111,0,0000,0,1000} (X mag=15, big X thrust)
X_PULL = {0,0100,0,0000,0,1000} (X mag=4, gentle pull)
Y_POS/Y_NEG = Y mag=15 with sign toggling (rotation simulation).
These are applied with precise timing using #delay statements to ensure they fall within the correct game phase.

🧩 Key Design Insights — Why These Modules Work Together

1. Clock Domain Crossing:
SPI master runs at 4 MHz, action_fsm at 100 MHz. The acl_data bus is latched on the negative edge of iclk (4 MHz) inside spi_master, then sampled by action_fsm at 100 MHz. Since 100 MHz is 25× faster than 4 MHz, the data is stable for many action_fsm cycles before changing — no metastability risk.
2. Parameterized Testability:
The CYCLES_PER_SEC parameter lets the testbench run the full 28-second game in ~300 µs of simulation time. All timing relationships are preserved (cooldowns, phase durations, baseline update rate all scale proportionally), so the testbench validates exactly the same logic as the real hardware.
3. Edge Detection Pattern:
Both modules use 1-cycle-delayed copies to detect rising edges: wire rise = signal & ~signal_d; This fires exactly once when a condition first becomes true, preventing continuous triggering while a gesture is held.
4. Global Reset via SW0:
The if (!start) block at line 121 acts as a synchronous global reset — it takes priority over the entire case (state) statement. Flipping SW0 OFF from any state (even S_DONE) instantly clears score, timers, and returns to S_IDLE. This is how the player restarts the game.
